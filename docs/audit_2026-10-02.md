# System audit — 2026-10-02

A full review of the repository and the **shared** deployment (shared ServiceNow instance and
shared EC2) carried out before any new Sprint 4 feature work. It was read-only against the
shared systems apart from one clearly labelled webhook event (section 4). Nothing was run
against a personal developer instance or a local stack.

Baseline: `main` at `710895a`, re-verified at `e065df9` after #189 and #209 merged during the
audit. "Fixed" below means fixed in the pull request that carries this document and covered
by a test; "Not fixed" says why.

## 2. Findings

Severity is the reviewer's judgement. **Fixed** items have regression tests.

| ID | Sev | Finding | Status |
|---|---|---|---|
| F-1 | **High** | **Follower reuse bypassed per-incident governance (#210).** A follower joining a *resolved* cluster had the leader's final resolution written to it as `complete` with no eligibility check, no input screening and no risk assessment, so a priority-1, Tier-1-service or MFA-reset incident that merely read like the leader skipped approval (PRD NFR-05, FR-13, FR-17). The #191 safety test still passed only because production no longer reached the graph path it tests. Proved by 5 of 6 risky followers being applied directly. | **Fixed.** `follower_reuse_verdict` runs the deterministic gates; only a clean, low-risk follower is reused (still zero LLM calls), everything else runs the full graph with the cached draft |
| F-2 | **High** | A failed ServiceNow write in that path was logged and swallowed; the follower was still marked `succeeded` and its cluster membership applied with nothing written. The execution-log write was swallowed with a bare `pass`. | **Fixed.** The failure propagates; a human lock becomes a terminal skip; the log failure is logged |
| F-3 | Medium | The semantic-cache threshold (0.76) is calibrated **in-sample**. The calibration reproduces exactly, but on an independent set 6 of 220 pairs resolved by different articles score at or above 0.76 (highest 0.838). The "zero false positives" claim does not generalise. | **Documented**; the cache comment and design doc are corrected. F-1's gate is what makes this safe |
| F-4 | **High** | **Secrets leaked through redaction into model prompts and traces:** any credential inside pasted JSON (`{"password": "…"}`), `secret_key=`, `AccountKey=`, `SharedAccessKey=`, `aws_secret_access_key`, `pass:` / `passcode` / PIN, `curl -u user:pass`, cookies, "the password for X is …", full-width `＝`. 11 of 30 forms leaked. | **Fixed.** 28 of 30 redacted; obfuscated e-mail and bare IPs are a stated non-goal |
| F-5 | **High** | **The LLM injection classifier ran before the eligibility check**, so text from locked, already-processed or AI-disabled incidents was sent to a model and a call was wasted (about 2 s and 800 tokens, seen in a live trace). A human-locked ticket is one an analyst has taken over. A unit test pinned the behaviour. | **Fixed.** Ineligible incidents skip every model layer |
| F-6 | Medium | **7 of 15 benign tickets were hard-blocked** by regex with no second look (XML `<system>` tags in logs, "from now on you must use MFA", "decode this … run it" in a procedure, a user called Dan). 15 of 33 disguised or translated attacks were caught by patterns. | **Fixed in part.** Ambiguous patterns now go to the fail-closed classifier; text is normalised (NFKC, zero-width, look-alikes); French/Spanish/Arabic overrides added. 25 of 33 caught, 1 of 15 benign blocked. The remaining one is "Ignore the previous instructions in KB0001", which is word-for-word the attack |
| F-7 | Medium | **The faithfulness backstop was never called.** `check_faithfulness` is documented as the deterministic guard against a hallucinated knowledge article, but only tests called it. An invented root cause or a wrong number would have been published and re-ingested as human knowledge. | **Fixed.** Capture refuses an article that states a number the human never gave, or whose content is more than half unsupplied; inflections and scaffolding words are not counted |
| F-8 | **High** | **`POST /approvals/{id}/decide` on a run with no stored interrupt returned 200**, wrote an immutable approval (the table is immutable by trigger, so it can never be corrected) and left the run parked. | **Fixed.** 409, nothing recorded. A legacy test that expected the bug was rewritten |
| F-9 | Low | No security headers on API responses (nosniff, framing, referrer, caching); the correlation id was echoed unvalidated. | **Fixed.** Middleware plus validation (`[A-Za-z0-9._:-]{1,128}`) |
| F-10 | Medium | Internal exception text reached API clients (503 bodies) and was persisted unredacted in failure rows, termination causes and cluster failure reasons. | **Fixed** |
| F-11 | Low | `reason` and `evidence` on a decision were unbounded and immutable. | **Fixed.** 4,000 characters / 16 KiB |
| F-12 | Medium | **An order-dependent test.** `test_ingest_failure_after_publish_is_drift_not_crash` fails under some random orders because `configure_logging` pinned module loggers for the life of the process, blinding `capture_logs`. A second unit test talked to whatever Redis was reachable. | **Fixed.** Logger caching only in production; the live-Redis test is marked `integration` |
| F-13 | Medium | **Documentation drift** (below). | **Fixed** |
| F-14 | Low | `GET /api/v1/config` reported `semantic_caching` from a decorative flag while the worker reads `ENABLE_SEMANTIC_CACHE`. | **Fixed** |
| F-15 | Low | The tool-registry doc listed the legitimate ServiceNow call sites as bounded; three direct callers outside the registry (the suggestions route, `incident_state.py`, `approval_capture.py`) were not listed and have no registry audit. | **Documented**, not refactored (follow-up) |
| F-16 | Low | #209 removed the blanket `data/*` ignore, so the copyrighted programme PDF could be committed by accident. | **Fixed.** `data/**/*.pdf` is ignored |

### Documentation drift (F-13)

README: S3.3 and S3.4 shown as in progress / in review (both merged); no Sprint 4; "thirteen"
Incident columns (fourteen); "`src/app/services/` is intentionally empty" (it holds the
clustering signature); the retrieval row listed `extraction.py` and `search.py` (a package and
a file that do not exist); the getting-started `docker compose up -d` also starts the API and
worker and then collides with `just run`; migrations and seeding were missing; `just check`
claimed to be "everything CI runs". `.env.example` carried a personal ngrok URL and two
settings that do not exist, and omitted `ENABLE_SEMANTIC_CACHE` and thirteen others. The
retrieval spec and state-schema doc pointed at files that moved; the schema doc said "exactly
seven tables" (nine) and the runbook gave migration head `0003` (it is `0005`). The guardrail
doc described a base64-length heuristic that #193 removed. The semantic-cache design described
the #191 behaviour that #210 reversed.

## 4. The one live write

same event id was posted 30 times:

- 1 accepted (`202`, `idempotent_replay=false`), 29 flagged `idempotent_replay=true`;

## 5. Not tested, and why

- **Operator-authenticated routes against the shared EC2** (config, approvals, DLQ, decide):
  the stored operator secret is stale (O-7) and no credential was read from the server. These
  routes are covered by in-process tests, not live ones.
- **The S1.2 permission harness** (`scripts/verify_permissions.py`): it appends undeletable
  rows to the shared Execution Log and creates an incident. Not run without explicit approval.
- **A live approve and a live reject on the shared system** (the S4.1 proof): needs test
  incidents on the shared instance and the operator credential.
- **The semantic classifier's detection rate**: needs a model call and a budget. Section 2's
  red-team numbers are the deterministic layer only; no combined figure is claimed.
- **Throughput and burst behaviour** on the shared host.
- **The PostgreSQL-backed suites** were not run locally (they need Docker); CI runs them.

- A first look at Langfuse suggested model, token and cost were missing from generations. That

  16 generations. Retracted.
- The 19 failures were first attributed to missing incidents. The numbers do exist on the
  shared instance; the `sys_id`s do not (O-2).
- A suspicion that `/api/v1/config` reports the wrong retrieval mode was checked and is wrong.
