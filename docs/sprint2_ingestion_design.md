## 1. Executive Summary & Architecture Overview

The BARQ Agentic Incident Resolution Platform ingests inbound ServiceNow incident events through a dedicated, asynchronous FastAPI webhook boundary:
`POST /api/v1/webhook/incident`

Per **FR-08**, the ingestion boundary must **never** block the request thread on downstream RAG retrieval, vector search, or LLM reasoning. The endpoint strictly executes four synchronous/asynchronous atomic phases before returning an immediate HTTP 202 Accepted response:
1. **Authentication & Contract v1 Validation**: Authenticates caller via Bearer token and validates payload against Outbound Event Contract v1.
2. **Atomic Idempotent Persistence**: Inserts the event into PostgreSQL (`idempotency_keys`, `events`, `executions`) within a single transactional boundary.
3. **Queue Enqueueing**: Enqueues new events into the primary Redis FIFO queue (`barq:incident:events`) in $O(1)$ constant time.
4. **Immediate 202 Response**: Returns acknowledgment with correlation ID and duplicate replay flag at a p95 **under 280 ms in the run tabulated in §5** — inside the 500 ms budget mandated by **NFR-01**. The margin is smaller than that figure suggests: across the five recorded runs of this same sweep, the worst p95 is 403.7 ms. See the run-note in §5.

## 2. Inbound Event Contract v1 & Schema Validation

The webhook strictly parses and enforces the Outbound Event Contract v1 schema:

### Payload Schema (`IncidentWebhookPayload`)
```json
{
  "event_id": "c7943a85-a835-423c-8231-282f4663f77a",
  "sys_id": "a1b2c3d4e5f60718293a4b5c6d7e8f90",
  "number": "INC0042567",
  "event_type": "incident.created",
  "contract_version": "v1"
}
```

* **`event_id`**: String identifier generated by ServiceNow; used as the deduplication token.
* **`sys_id`**: 32-character hexadecimal string representing the ServiceNow incident record sys_id.
* **`number`**: Incident ticket reference (e.g. `INC0042567`).
* **`event_type`**: Literal enum constraint (`incident.created` or `incident.updated`).
* **`contract_version`**: Optional, defaults to `"v1"` when the producer omits it (the deployed S1.3 script action sends no version field — #137). Unsupported values are rejected with HTTP 422.

## 3. Atomic Database Idempotency & Deduplication (EC-01)

Duplicate event deliveries (network retries or redeliveries from ServiceNow) are arbitrated directly by PostgreSQL without table locks or read-before-write race conditions:

1. **Idempotency Gate**: The `idempotency_keys` table holds a unique constraint on `event_id` (`uq_idempotency_keys_event_id`).
2. **Pipelined Insert**: `IdempotencyKey`, `Event`, and `Execution` entities are staged in SQLAlchemy memory and committed in a single database round-trip.
3. **Integrity Arbitration**:
   * If the event ID is fresh, PostgreSQL writes all 3 records and returns status `accepted`. The event is then enqueued to Redis.
   * If the event ID already exists, PostgreSQL throws a unique constraint violation (`uq_idempotency_keys_event_id` or `uq_events_event_id`). The repository catches this, rolls back cleanly, and returns status `duplicate`.
   * Duplicate events return immediate `HTTP 202 Accepted` with `idempotent_replay: true` and are **not** re-enqueued to Redis.

$$\text{Acknowledgement Latency } p95 < 500\text{ ms across all queue depths (0, 1k, 10k)}$$

Because Redis `LPUSH` is strictly an $O(1)$ constant-time operation, pushing to an empty queue or a queue with 10,000 pre-existing items exhibits identical performance.

## 6. Dead-Letter Queue (DLQ) & Operator Replay Semantics

When downstream asynchronous workers encounter persistent unrecoverable failures (e.g. poison payloads, schema mismatch, or retry exhaustion after 3 backoff attempts):
1. The failing worker moves the incident payload from `barq:incident:events` to `barq:incident:dlq`.
2. Operators inspect failed events via `GET /api/v1/dlq`.
3. Operators replay failed events via `POST /api/v1/dlq/{event_id}/replay` (enforced by the `operator` role in the request's JWT).
4. Replaying pops the item from the DLQ and pushes it back into `barq:incident:events` for immediate reprocessing without losing audit trace state.
