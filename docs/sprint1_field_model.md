## Design contract

The Incident table is the platform contract between ServiceNow and the external orchestrator. The model records whether AI processing is allowed, its lifecycle, the agent's output and confidence, exact model/code attribution, timing, human-control state, the final outcome, and explicit failure information.

All fields must be created while **AI Incident Orchestrator** is the active application. The exact technical names must use the scope prefix generated by ServiceNow. No field or supporting artifact may be created in the Global application scope.

## Suggestion and resolution separation

**AI Suggestion** records what the model proposed before approval or execution. **AI Resolution** records the final action or outcome actually accepted and applied. They remain independent because a reviewer may reject or modify the suggestion, a tool may fail while executing it, or the final resolution may differ after investigation. Separate fields preserve the original proposal, prevent evidence loss, support human-in-the-loop auditing, and allow evaluation of proposal quality against real outcomes.

## Lifecycle semantics

1. An authorized user enables AI processing, if the optional AI Enabled field is approved.
2. An eligible Incident enters `pending`.
3. A worker claims it and writes `in_progress` plus Processing Start.
4. The agent writes classification, confidence, suggestion, model name, and agent version.
5. High-risk or low-confidence work enters `awaiting_approval` and sets Human Review Required.
6. A successful approved/safe action writes Resolution, Processing End, and `complete`.
7. An unsuccessful run writes Failure Reason, Processing End, and `failed`.
8. Human Lock overrides every automated transition and write.

## Validation rules

- AI Confidence is optional before scoring but, when present, must be numeric and between 0 and 1 inclusive.
- Processing End must be blank or greater than/equal to Processing Start.
- Failed processing should include a non-empty Failure Reason.
- Complete processing should include Processing End and a final Resolution.
- Human Lock must be checked by the Sprint 2 eligibility Business Rule and again before any automated write to prevent a race after work has been queued.
- Scripts must use internal choice values, not display labels.
